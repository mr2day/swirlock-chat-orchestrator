# Transport And Routing Plan

## Goal

Move the orchestrator toward the intended fast-path architecture:

- every hot service-to-service relationship uses a long-lived WebSocket
- request/response work is multiplexed over that socket by `correlationId`
- user-visible assistant text is always generated by the final-answer LLM
- turn routing is semantic, fast, and structured
- the Utility LLM is a fallback router, not the default path for obvious turns

This document is a plan only. It does not change runtime behavior by itself.

## Non-Negotiables

- No canned answers anywhere in the orchestrator.
- No hardcoded word matching for user intent.
- The Utility LLM and embedding router may classify or route only; they must not
  generate user-visible replies.
- The final-answer LLM is the only component that writes assistant response
  text.
- Hot-path service calls should not open a fresh HTTP request or WebSocket per
  turn once the persistent protocol exists.
- Every message crossing a service boundary needs a correlation ID, deadline,
  priority where relevant, and structured error behavior.

## Current State

Already good:

- UI to Chat Orchestrator uses a persistent session WebSocket.
- The orchestrator no longer has canned answers.
- The orchestrator already has a Utility LLM classifier with JSON output,
  thinking disabled, and no conversation persistence.
- The orchestrator can already route a turn to final-answer generation without
  RAG or thinking when the classifier returns that structured decision.

Still wrong for the target architecture:

- Orchestrator to Utility LLM classification uses HTTP `POST /v2/infer`.
- Orchestrator to final-answer Model Host opens a new WebSocket per turn at
  `/v2/infer/stream`.
- Orchestrator to RAG Engine opens a new WebSocket per retrieval request.
- RAG Engine to Embedding Service uses HTTP for embeddings.
- The v3 Model Host contract currently documents `/v2/infer/stream` as one
  inference request per WebSocket connection, so a persistent multiplexed
  service stream needs a contract update before it becomes the canonical path.

## Target Architecture

Each service pair keeps a dedicated long-lived WebSocket.

```text
Chatbot UI <-> Chat Orchestrator
Chat Orchestrator <-> Primary LLM Host
Chat Orchestrator <-> Utility LLM Host
Chat Orchestrator <-> RAG Engine
Chat Orchestrator <-> Embedding Service
RAG Engine <-> Embedding Service
RAG Engine <-> Utility LLM Host
```

The exact service pairs may vary by deployment, but the rule is the same: a
service opens its upstream sockets at startup, keeps them warm, sends all hot
requests over those sockets, and reconnects on failure.

## Persistent Service Stream Protocol

Add a multiplexed service WebSocket protocol to the contracts before making the
orchestrator depend on it.

Candidate path names:

- Model Host: `/v2/infer/service-stream`
- RAG Engine: `/v2/retrieval/evidence/service-stream`
- Embedding Service: `/v2/embeddings/service-stream`

Client to server messages:

```json
{
  "type": "infer",
  "correlationId": "turn-123",
  "request": {
    "requestContext": {
      "callerService": "chat-orchestrator",
      "requestedAt": "2026-05-06T00:00:00.000Z",
      "priority": 50,
      "timeoutMs": 30000
    },
    "input": { "parts": [] },
    "options": { "thinking": false, "responseFormat": "json" }
  }
}
```

Server to client messages:

```json
{ "type": "accepted", "correlationId": "turn-123", "meta": {} }
{ "type": "queued", "correlationId": "turn-123", "data": {} }
{ "type": "started", "correlationId": "turn-123", "meta": {} }
{ "type": "thinking", "correlationId": "turn-123", "data": { "text": "" } }
{ "type": "chunk", "correlationId": "turn-123", "data": { "text": "" } }
{ "type": "done", "correlationId": "turn-123", "data": {} }
{ "type": "error", "correlationId": "turn-123", "error": {} }
```

Control messages:

- `ping`
- `pong`
- `cancel`
- `draining`
- `ready`

The client must keep a pending request map by `correlationId`. The server may
process multiple in-flight requests concurrently if the hosted resource can
support it, or queue them internally if it cannot.

## Semantic Turn Router

Add an embedding-based router before the Utility LLM classifier.

Flow:

```text
user turn
  -> SemanticTurnRouter
      -> high confidence: use semantic routing decision
      -> low/ambiguous confidence: ask Utility LLM classifier
  -> PromptBuilder
  -> final-answer LLM
```

The semantic router owns no user-visible text. It only returns routing fields:

```json
{
  "route": "final_answer",
  "shouldRetrieve": false,
  "shouldThink": false,
  "includeMemoryInPrompt": false,
  "includeRecentConversationInPrompt": false,
  "intent": "assistant_identity",
  "confidence": "high",
  "reason": "semantic router matched assistant identity examples"
}
```

Startup behavior:

1. Load intent labels and examples from a committed config file.
2. Embed every label/example once.
3. Cache vectors in memory.
4. Refuse semantic routing if the Embedding Service is unavailable; fall back to
   the Utility LLM classifier.

Per-turn behavior:

1. Embed the current user message.
2. Compare against intent vectors using cosine similarity.
3. Compute top score and margin over the second score.
4. Use the semantic decision only if score and margin exceed thresholds.
5. Otherwise fall back to Utility LLM classification.

Initial intent labels:

- `pure_chat`
- `assistant_identity`
- `assistant_capability`
- `coding_request`
- `creative_generation`
- `needs_current_info`
- `needs_rag`
- `needs_multistep_thinking`
- `clarification_needed`
- `follow_up_question`
- `image_understanding`

Important model note: the current embedding setup appears to assume
`bge-small-en-v1.5`. That is not ideal for Romanian or multilingual routing.
Before relying heavily on semantic routing, choose a multilingual embedding
model and update dimensions/config consistently across services.

## Implementation Phases

### Phase 1: Contract And Protocol Design

Deliverables:

- Update contracts v3 with persistent multiplexed service streams.
- Define shared event envelopes, control messages, cancellation, timeouts, and
  reconnect behavior.
- Decide whether existing one-request WebSocket endpoints stay as compatibility
  endpoints or become deprecated.

Exit criteria:

- Contracts describe persistent service streams for Model Host, RAG Engine, and
  Embedding Service.
- The one-request-per-WebSocket limitation is no longer the only documented
  model-host stream behavior.

### Phase 2: Shared Service Socket Client

Deliverables:

- Add a reusable client abstraction in the orchestrator:
  - connect on application startup
  - heartbeat
  - reconnect with backoff
  - pending request map
  - request timeout cleanup
  - cancellation
  - backpressure / max in-flight guard
  - health state
- Keep existing HTTP/per-request WebSocket clients as fallback during migration.

Exit criteria:

- The orchestrator can maintain a persistent upstream socket and execute a
  request/stream lifecycle over it in tests.

### Phase 3: LLM Host Persistent Transport

Deliverables:

- Implement persistent service stream support in `swirlock-llm-host`.
- Replace orchestrator Utility LLM HTTP calls with persistent socket calls.
- Replace orchestrator final-answer per-turn WebSocket calls with persistent
  socket calls.

Exit criteria:

- One orchestrator to LLM Host socket handles both Utility and final-answer
  requests.
- Utility classifier still uses `thinking=false`, JSON response format, and
  never persists as conversation history.
- Final-answer requests still stream `queued`, `started`, `thinking`, `chunk`,
  `done`, and `error` to the UI.

### Phase 4: Semantic Router

Deliverables:

- Add `SemanticTurnRouterService` in the orchestrator.
- Add committed intent examples/config.
- Add an embedding client path for router calls.
- Use semantic routing before Utility LLM classification.
- Add diagnostics indicating whether the route came from semantic router or
  Utility LLM fallback.

Exit criteria:

- Obvious routing decisions avoid Utility LLM latency.
- Ambiguous decisions fall back to Utility LLM.
- Regression tests cover greetings, Romanian assistant identity, current-info
  queries, coding requests, and ambiguous follow-ups.

### Phase 5: RAG And Embedding Persistent Transport

Deliverables:

- Add persistent service stream support to RAG Engine.
- Add persistent service stream support to Embedding Service.
- Move orchestrator to RAG Engine retrieval calls onto persistent sockets.
- Move RAG Engine query/document embedding calls onto persistent sockets.
- Move orchestrator semantic-router embedding calls onto persistent sockets.

Exit criteria:

- No hot-path ecosystem component uses per-turn HTTP or per-request WebSocket
  calls when a persistent upstream service is available.

### Phase 6: Observability And Performance Gates

Deliverables:

- Add per-stage timings:
  - semantic routing
  - Utility LLM fallback
  - memory/context assembly
  - RAG retrieval
  - final-answer queue wait
  - first token latency
  - total turn latency
- Add connection health diagnostics for every upstream persistent socket.
- Add tests for reconnect, pending request failure, cancellation, timeout, and
  backpressure.

Exit criteria:

- A local benchmark shows lower median and p95 latency than the current
  per-call transport.
- Failures are visible and actionable in diagnostics.

## Suggested Build Order

1. Update contracts for persistent multiplexed service streams.
2. Implement the shared persistent socket client in the orchestrator.
3. Add persistent stream support to LLM Host.
4. Move Utility and final-answer LLM calls to the persistent LLM socket.
5. Add the semantic router using the existing embedding HTTP endpoint as a
   temporary bridge.
6. Move Embedding Service and RAG Engine to persistent service streams.
7. Tune thresholds and benchmark latency.

This order reduces risk: first fix the transport foundation for the highest
latency path, then add semantic routing, then finish the ecosystem-wide
persistent transport migration.

## Open Decisions

- Which multilingual embedding model should replace or supplement
  `bge-small-en-v1.5`?
- Should the semantic router live only inside the orchestrator, or become a
  reusable package/config shared by future agents?
- What are the first production thresholds for score and score margin?
- Do we keep one-request WebSocket endpoints permanently for compatibility, or
  deprecate them after the persistent service stream is stable?
- How should pending in-flight requests behave after reconnect: fail fast,
  retry only idempotent internal calls, or let each caller specify policy?

## Immediate Next Task

Create the v3 contract change for persistent multiplexed service streams. The
orchestrator should not hard-depend on a protocol that the contracts still
describe as one request per WebSocket connection.
